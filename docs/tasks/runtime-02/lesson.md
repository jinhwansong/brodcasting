# 창구와 작업실은 시작 방법이 달라요

편의점의 접수 창구는 손님 말을 듣습니다. 택배 분류실은 쌓인 상자를 정리합니다. 같은 회사의 규칙을 쓰더라도 각각 필요한 도구가 다릅니다.

**HTTP API**는 요청을 받을 문을 열어야 합니다. NestFactory.create로 앱을 만들고 listen으로 포트를 엽니다. 포트는 컴퓨터가 어떤 프로그램에 요청을 전달할지 구분하는 번호입니다. 이번 API의 창구는 /health 하나입니다.

**application context**는 Nest의 서비스 생성·연결 기능을 쓰면서 HTTP 문은 열지 않습니다. NestFactory.createApplicationContext를 사용합니다. [공식 독립 애플리케이션 문서](https://docs.nestjs.com/standalone-applications)를 확인하세요. API의 Guard나 HTTP Pipe가 application context에서 자동 실행되는 것은 아닙니다. 큐 입력 검증은 다음 단계에서 따로 연결해야 합니다.

Module은 설계도에 가깝습니다. ‘이 부품을 준비하자’고 적는 것이지, 실행 중인 운영체제 프로세스를 새로 만드는 명령이 아닙니다. 두 시작점 파일을 각각 node로 실행하기 때문에 **프로세스 두 개**가 생깁니다.

ActivityService는 시작할 때 bootId 하나를 만들고 횟수를 기억합니다. API 안의 두 요청은 같은 Nest 서비스 인스턴스를 쓰므로 같은 bootId와 늘어난 횟수를 봅니다. 별도 Worker는 같은 소스를 읽어도 자기 객체를 새로 만들므로 다른 bootId를 봅니다. 같은 파일을 import했다고 메모리가 합쳐지지 않습니다.

프로세스를 나누면 Worker를 닫아도 API의 코드 실행은 계속할 수 있습니다. 다만 같은 CPU·RAM을 쓰면 서로 느려질 수 있고, 공유 DB가 멈추면 둘 다 영향을 받을 수 있습니다. **장애 경계가 생긴 것과 모든 장애가 격리된 것은 다릅니다.** 성능·자원 경쟁은6주에 실제 측정합니다.

## 끝낼 때도 순서가 있어요

타이머는 ‘다음에도 또 실행하자’는 약속입니다. context만 닫고 타이머를 남기면 프로세스가 계속 살아 있을 수 있습니다. 이번 제공 코드는 타이머를 지우고 app.close를 기다린 뒤 부모와의 통신도 닫습니다. [Nest 종료 수명](https://docs.nestjs.com/fundamentals/lifecycle-events)을 참고하세요. 운영 중인 프로세스를 무조건 강제로 끄는 것과 정상 종료 절차를 비교하세요.

이번에는 아직 큐가 없습니다. Worker가 만든 횟수는 재시작하면0부터 다시 시작합니다. ‘일을 다른 곳에 맡겼다’고 자동으로 저장·재시도까지 되는 것은 아닙니다. 다음 주에는 Redis에 작업을 넣고 BullMQ Worker가 꺼내도록 바꿉니다.
