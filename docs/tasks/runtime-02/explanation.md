# 첫 시도 뒤 확인하는 해설

두 함수의 차이는 모듈 이름뿐 아니라 **NestFactory의 생성 함수**입니다. HTTP 앱은 컨트롤러를 요청 경로에 연결하고 application context는 제공자들을 생성합니다. main.ts의 역할까지 context 함수에 넣으면 listen이나 종료 처리가 중복됩니다.

프로세스를 나누는 코드는 이 두 함수가 아니라 node로 시작점을 각각 실행하는 곳입니다. 공개 검사는 fork로 실제 프로세스 두 개를 띄웁니다. 모의 API나 한 프로세스 안의 객체 두 개로 이 검증을 대신하지 않습니다.

비정상 종료는 가짜 Worker 안의 process.exit(7)로 재현합니다. 반면 정상 종료 검사는 IPC stop을 받아 app.close 뒤 끝나는 경로를 확인합니다. Windows에서 SIGTERM이 강제 종료처럼 동작하는 경우가 있으므로 이번 로컬 결과를 POSIX 신호 정리의 증거로 부르지 않습니다.

기본 준비 확인은15초 상한입니다. 최초 모듈 로딩이 느린 Windows에서5초가 부족한 실제 실행을 확인해 조정했습니다. 이 대기 제한은 서버 응답 성능 합격선이 아닙니다. 요청이 영원히 준비되지 않는 오류를 감추지 않도록 여전히 시간 초과 시 실패합니다.

참고 완성본에는 독립 변경의 종료 중 작업 처리 답이 없습니다.
