# F2 — 로그인과 권한, 늦게 도착한 응답

A 계정에서 요청한 결과가 늦게 도착할 수 있어요. 그 사이 B 계정으로 바뀌었다면 A의 알림을 B의 화면에 보여 주면 안 됩니다.

## 먼저 예상하기

실행 전에 무엇이 성공하고 무엇이 거부돼야 하는지 적으세요. client/src/response-guard.ts의 mayApplyResponse 함수를 직접 구현합니다. 참고 완성본은 첫 구현 뒤에 비교하세요.

## 실습 순서

1. npm ci 후 npm run check를 실행합니다. 실제 DB·Redis 검사와 화면 검사가 함께 실행됩니다.
2. 요청 당시 계정 번호와 현재 계정 번호가 같고 화면이 살아 있을 때만 응답을 적용하도록 구현합니다. 음수나 잘못된 번호는 받지 않습니다.
3. node dev-lab.mjs로 로컬 실습을 켭니다. 두 계정을 만들고 각자 알림이 섞이지 않는지 확인합니다.
4. 로그아웃 후 알림 요청이 거부되는지 확인합니다. 401은 재인증, 403은 해당 요청 거부입니다. 네트워크 오류를 저장 성공으로 표시하지 않습니다.
5. 개발자 도구에서 버튼 표시를 바꿔도 서버가 다른 사용자의 알림을 반환하지 않는다는 것을 직접 HTTP 검사와 비교합니다. CSRF 누락과 다른 Origin도 서버가 거부해야 합니다.

## 설명3개

1. 화면의 버튼 숨김과 서버 권한 검사가 다른 이유는 무엇인가요?
2. HttpOnly·Secure·SameSite가 각각 무엇을 제한하나요?
3. A의 응답이 B 로그인 뒤 도착할 때 버리는 기준은 무엇인가요?

## 독립 변경

다른 탭의 계정 변경 신호를 받으면 서버 세션을 다시 확인하는 흐름을 직접 설계하세요. 신호에 토큰을 넣지 않고 신호 자체를 인증 근거로 삼지 않습니다. 이 과제의 완성 코드는 제공하지 않습니다.
