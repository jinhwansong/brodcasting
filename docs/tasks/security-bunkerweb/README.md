# 맨 마지막 강의 — BunkerWeb과 방송 서비스 인프라 보안

기본 0~11단계, 알림 추가 과정, [프론트·서버 보안 과제](../../../SECURITY_CURRICULUM.md)를 마친 **전체 과정의 마지막 강의**입니다. 2주, 주당 6~8시간을 권장합니다. 자신의 방송 실습 앱 앞에 보호 계층을 두고 정상 요청·차단·오탐·복구를 구분하는 것이 목표입니다.

이 문서는 **강의 본문·실습 설계·검증 행렬**입니다. 아직 이 저장소에 버전을 고정한 BunkerWeb Compose 구현이나 실제 실행 증거는 없습니다. 이번 교재 작성 중 Docker·BunkerWeb·TLS·공개 서버를 설치하거나 배포하지 않았습니다. 후속 구현 때 공식 자료와 버전을 다시 확인하고 로컬 환경에서 검증합니다.

## 선수 지식과 환경 경계

- Docker Compose의 service·network·volume·port·healthcheck, Linux 프로세스·로그·파일 권한을 설명할 수 있어야 합니다.
- HTTP 요청, TLS 종료, 브라우저 origin, HTTP API와 Socket.IO 연결, 프록시를 거친 클라이언트 주소를 배운 뒤 진행합니다.
- 공식 [Quickstart](https://docs.bunkerweb.io/latest/quickstart-guide/)는 인터넷 접근과 도메인을 전제로 하는 부분이 있습니다. 학습 초기에는 **본인 로컬 전용**으로 구성하고 공개 포트·도메인·인증서 발급 절차를 그대로 복사하지 않습니다.
- 공개 진입점은 로컬 loopback에만 바인딩합니다. 앱·DB·Redis와 관리용 API/UI는 외부에 공개하지 않고 필요한 컨테이너 네트워크만 연결합니다. Docker 내부 연결과 호스트 포트 공개는 다르게 기록합니다.
- TLS는 처음에 로컬 전용 인증서로 실습하고 클라이언트가 명시적으로 신뢰하도록 합니다. 검증을 끄는 옵션으로 TLS 통과를 기록하지 않습니다. 개인 키와 관리 비밀번호는 저장소 밖에서 주입합니다.
- Docker socket 접근, 호스트 네트워크, privileged 권한을 관성적으로 추가하지 않습니다. 공식 예제가 요구하는 권한을 읽고 이번 통합 방식에서 필요한지 결정합니다.

## 먼저 예상하기

[제출 양식](submission.md)에 다음을 적으세요.

1. 브라우저 요청은 어느 지점에서 TLS가 끝나고 어느 경로로 앱에 도착하나요? DB·Redis·관리 UI에 접근 가능한 주체는 누구인가요?
2. WAF가 허용한 요청이 다른 사람의 즐겨찾기를 바꾸려 한다면 어느 계층에서 거부해야 하나요?
3. 정상 채팅이 403으로 차단되면 WAF·앱·프록시 중 어디를 먼저 확인하나요? 전체 보호 기능을 끄지 않고 좁힐 증거는 무엇인가요?

## 1주 — 요청 경로와 경계 만들기

### 1. 구성과 버전 고정

공식 [개념](https://docs.bunkerweb.io/latest/concepts/)·[Docker 통합](https://docs.bunkerweb.io/latest/integrations/)을 읽고 학습 환경에 맞는 한 가지 통합 방식을 고르세요. 이미지 버전·가능하면 digest·설정 출처·날짜를 기록합니다. 2026-10-17 열람한 공식 예제에는 1.6.16이 쓰였지만, 이를 미래의 최신 버전이나 이 저장소에서 실행한 버전으로 취급하지 않습니다.

앱 요청 처리, BunkerWeb 보호/프록시, 설정 생성·적용, 관리 화면의 책임을 나눠 적으세요. 선택한 방식에 따라 구성요소가 달라집니다. 우선 수동 Docker Compose 방식으로 네트워크와 설정 반영을 이해하고 자동 검색·Kubernetes 확장은 뒤로 둡니다. 유료 플러그인은 필수 과제가 아닙니다.

### 2. 정상 경로 먼저

WAF 규칙을 조정하기 전에 정적 페이지·목록 API·로그인·즐겨찾기·채팅·테스트 영상의 정상 기준선을 남깁니다. 프록시를 거치지 않는 앱의 호스트 포트는 진단용 로컬 브랜치 외에는 공개하지 않습니다. 최종 구성에서 보호 계층 우회 경로가 남아 있는지 확인하세요.

HTTP와 Socket.IO의 초기 HTTP 요청·업그레이드·재연결을 따로 관찰합니다. [Reverse proxy 기능](https://docs.bunkerweb.io/latest/features/#reverse-proxy)의 WebSocket 지원과 시간 제한을 해당 버전에서 확인하세요. 현재 문서의 `REVERSE_PROXY_WS` 같은 설정 이름은 **확인할 단서**이며, 설정 파일을 만들 때 정확한 버전의 적용 위치·기본값을 다시 확인합니다.

### 3. TLS·헤더·실제 주소

인증서 이름·신뢰·만료, HTTPS/WSS 연결, 프록시 뒤 쿠키와 리다이렉트를 확인합니다. 앱이 믿을 프록시 범위를 명시하고 클라이언트가 임의로 보낸 전달 헤더를 신원이나 무제한 요청 허용 근거로 사용하지 않습니다. 잘못된 real-IP 설정이 요청 제한과 로그를 어떻게 흐리는지 가짜 데이터로 비교하세요. F3의 CSP·보안 헤더를 실제 응답에서 확인하며 프록시와 앱이 서로 다른 정책을 중복 설정하지 않았는지 조사합니다.

## 2주 — 탐지·차단·오탐·복구

### 4. 관찰과 차단 구분

[기능 문서](https://docs.bunkerweb.io/latest/features/)에서 전역 보안 모드와 ModSecurity/OWASP CRS의 탐지·차단 설정을 구분합니다. 현재 문서에는 `SECURITY_MODE`, `MODSECURITY_SEC_RULE_ENGINE` 등이 설명되어 있습니다. 서로 다른 플러그인의 효과를 한 설정으로 추측하지 말고, 선택 버전의 유효 설정과 응답·로그를 함께 확인하세요.

처음에는 탐지 모드에서 정상 요청을 관찰하고, 격리된 실습 브랜치에서 차단 모드로 바꿔 비교합니다. 로컬 요청 식별용 **무해한 표식과 학습용 사용자 정의 테스트 규칙**으로 탐지/차단 경로를 확인한 뒤, 공식 자료의 제한된 CRS 검증 사례를 본인 로컬 서비스에서만 사용합니다. 표식 규칙의 성공은 CRS 전체나 실서비스 공격 방어를 검증한 것이 아닙니다.

### 5. 정상 요청을 차단했을 때

한글 채팅·검색·긴 정상 제목 등 실제 제품 입력을 낮은 빈도로 재생하세요. 정상 요청이 차단되면 [문제 해결 문서](https://docs.bunkerweb.io/latest/troubleshooting/)를 참고해 요청 식별자·시각·경로·규칙 id·판단 점수·앱 로그를 연결합니다. 전체 WAF나 넓은 경로의 검사를 끄는 대신 **특정 서비스·경로·필드·규칙의 필요한 최소 범위**로 예외를 제안합니다. 변경 전후 정상 경로와 거부돼야 할 경로를 모두 다시 검사하세요.

### 6. 가용성과 메시지 경계

9단계에서 정한 작은 로컬 조건을 사용해 요청/연결 제한·초과 응답·회복을 확인합니다. 임의의 대량 트래픽을 만들지 않습니다. 연결이 살아 있다는 것과 메시지를 처리할 권한이 있다는 것은 별도입니다. WebSocket 업그레이드 전후의 검사 범위를 기록하고, 연결 이후 메시지의 방 권한·길이·빈도·세션 폐기는 앱에서 계속 검증합니다. WAF가 모든 소켓 프레임이나 외부 미디어/CDN 경로를 자동으로 검사한다고 가정하지 않습니다.

### 7. 잘못된 설정에서 되돌리기

정상 설정과 이미지 버전을 보관한 뒤 잘못된 upstream 또는 좁은 테스트 차단 규칙으로 오류를 재현합니다. 설정 검사·적용 실패, 프록시 502, WAF 403, 앱 403을 구분하세요. 이전 정상 설정으로 되돌리고 HTTP·로그인·채팅 재연결·데이터 불변을 다시 확인합니다. 복구를 이유로 DB 볼륨이나 사용자 데이터를 지우지 않습니다. 설정 백업을 복원하는 것과 앱 DB 백업 복원도 구분합니다.

## 제출할 검증 행렬

아래는 **모두 미실행**입니다. 실제 실행 후 기대/실제·설정 커밋·정제된 로그를 채웁니다.

| 확인 | 기대 증거 | 현재 상태 |
| --- | --- | --- |
| 프록시의 정상 페이지·API | 올바른 라우팅과 HTTP 응답, 앱 로그의 같은 요청 | 미실행 |
| 외부에서 앱·DB·Redis·관리 경로 직접 접근 | 정의한 네트워크 경계대로 접근 불가 | 미실행 |
| TLS·HTTPS/WSS·쿠키·헤더 | 신뢰 가능한 인증서와 선택 정책, 검증 생략 없음 | 미실행 |
| Socket.IO 연결·업그레이드·재연결 | 선택 transport 별 정상 흐름과 타임아웃 근거 | 미실행 |
| 일반 사용자의 관리자 변경 | WAF 통과 여부와 별개로 앱 권한 거부·데이터 불변 | 미실행 |
| 테스트 규칙 탐지 / 차단 | 로그만 남음과 실제 거부를 분리한 기록 | 미실행 |
| 정상 입력 오탐과 최소 예외 | 원인 규칙·예외 범위·정상/거부 회귀 | 미실행 |
| 낮은 로컬 요청 제한·회복 | 조건·상한·초과·해제 후 회복, 중단 기준 | 미실행 |
| 잘못된 upstream·설정 되돌림 | 원인 계층·복구 절차·복구 후 핵심 회귀 | 미실행 |
| 영상·자막·외부 경로 | 실제 통과 경로와 WAF 밖 경로를 구분 | 미실행 |

로그에서 토큰·세션·개인정보·채팅 전문을 제거하고 관찰에 필요한 메타데이터만 남깁니다. 브라우저 항목은 사용자 추후 검증 전까지 체크하지 않습니다.

## 설명 3개와 독립 변경

1. 한 요청의 DNS/연결·TLS·프록시·WAF·앱·DB 경로에서 각 계층이 신뢰하는 값과 거부할 수 있는 문제를 설명하세요. 자신의 구성도에 공개/내부 포트를 표시합니다.
2. 403 하나를 WAF와 앱 중 어디서 만들었는지 증거로 구분하고, 선택한 예외가 다른 방의 권한 검사와 어떤 관계인지 설명하세요.
3. 정상 설정으로 되돌렸다는 증거와 여전히 검증하지 못한 위험을 설명하세요. 작은 로컬 실험을 운영 수용량으로 일반화하지 않습니다.

독립 변경: 특정 경로의 정상 입력 하나가 테스트 규칙에 걸리게 만든 뒤, 서비스 전체를 해제하지 않고 그 입력에 필요한 범위만 조정하세요. 다른 경로의 테스트 표식은 계속 차단되고 앱의 사용자·방 권한 검사는 유지되어야 합니다. 수정 전 실패, 수정 후 정상, 거부 경로 회귀, 원복까지 직접 증명하세요.

## 최종 통과와 남는 일

구성도·고정 버전·설정 diff·검증 행렬·오탐 분석·복구 기록·설명·독립 변경을 함께 평가합니다. 실제 운영 전에는 서비스별 위협 모델·운영 인력·업데이트·모니터링·악용 대응·비용을 추가로 결정합니다. 이 마지막 실습을 완료했다는 사실만으로 공개 운영 승인을 얻거나 보안 인증을 받은 것은 아닙니다.
