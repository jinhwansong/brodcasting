# 접수한 일과 처리 중인 일은 달라요

식당에서 주문서를 받는 사람과 요리하는 사람이 다를 수 있습니다. 주문서를 주방 앞에 쌓아 두면 요리사가 잠시 자리를 비워도 어떤 주문이 남았는지 알 수 있습니다.

API는 접수하는 사람, Redis는 작업 정보를 두는 곳, BullMQ는 작업 상태·잠금·재시도를 다루는 도구, Worker는 꺼낸 일을 실행하는 사람에 가깝습니다. Redis가 사람이나 실행 코드인 것은 아닙니다. 또 BullMQ Worker라는 객체가 자동으로 새 운영체제 프로세스를 만드는 것도 아닙니다. 이번에는2주처럼 시작점 파일을 각각 node로 실행했기 때문에 프로세스가 나뉩니다.

**waiting**은 아직 대기, **active**는 처리 중, **completed**는 처리 함수가 성공, **failed**는 정해진 시도 안에 끝내지 못한 상태입니다. API가 접수를 성공했다고 답한 것과 발송이 완료된 것은 다른 순간입니다. 사용자 화면에서도 두 상태를 구분해야 합니다.

이번 가짜 처리 함수는 failures가2면 처음 두 번 오류를 내고 세 번째에 성공합니다. attempts3은 ‘처음 한 번과 재시도 두 번을 합한 최대 세 번’입니다. 실패 사이100ms는 서버가 잠깐 숨을 돌리게 하는 대기입니다. 실제 서비스의 재시도 간격을 이 실험 숫자 그대로 정하지 않습니다. [실패 재시도 공식 문서](https://docs.bullmq.io/guide/retrying-failing-jobs)를 확인하세요.

## 같은 주문 번호면 언제나 한 번일까요?

큐에 해당 ID의 기록이 **남아 있을 때** 같은 ID를 넣으면 새 작업이 생기지 않습니다. 그러나 기록을 지운 뒤에는 새로 생길 수 있습니다. 기록을 영원히 남기면 메모리도 계속 필요합니다. 이번에는 완료/실패 기록 각각100개 또는1시간이라는 상한을 둡니다. 정리 조건이 지난 기록은 다음 완료/실패 시점에 정리될 수 있으므로 정확히1시간에 지우는 타이머라고 생각하지 마세요.

더 중요한 예가 있습니다. Worker가 실제 결과를 저장했는데 큐에 성공을 알리기 전에 꺼지면 다시 실행될 수 있습니다. ‘작업 ID가 있으니 외부 발송도 반드시 한 번’이라고 주장하면 안 됩니다. 다음4주에서는 **같은 일을 다시 처리해도 저장 결과가 겹치지 않게 하는 멱등성**을 배웁니다. [Job ID 문서](https://docs.bullmq.io/guide/jobs/job-ids)와 [멱등 작업](https://docs.bullmq.io/patterns/idempotent-jobs)을 읽으세요.

## 끄는 순간도 처리의 일부예요

Worker.close는 새 작업을 받지 않게 하고 진행 중인 처리의 끝을 기다립니다. 이번 검사는 처리 함수를 잠시 기다리게 한 뒤 close가 먼저 끝나지 않는지 실제로 확인합니다. 이것은 강제로 프로세스를 죽이는 것과 다릅니다. 강제 종료로 남은 작업의 회수·중복 경계도 계속 생각해야 합니다. [정상 종료 문서](https://docs.bullmq.io/guide/workers/graceful-shutdown)를 참고하세요.

코드에서 비밀번호·쿠키·대화 전문을 작업 데이터로 넣지 않습니다. 이번 입력에는 가짜 ID와 실패 횟수만 있습니다. Redis를 인터넷에 열거나 익숙한 운영 Redis에 실험 작업을 넣지 않습니다.7주에서는 API/Worker/Redis/DB를 내부 네트워크에 연결하고 영속 저장·복구를 검증합니다.
