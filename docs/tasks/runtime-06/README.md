# 알림6주 — 바쁜 서버를 숫자로 보기

API는 주문을 받는 직원, Worker는 일을 처리하는 직원이라고 생각해요. 두 직원은 다른 프로그램이므로 CPU와 메모리도 따로 봐야 합니다.

## 먼저 예상하기

실행 전에 무엇이 성공하고 무엇이 거부돼야 하는지 적으세요. src/summary.mjs의 summarize 함수를 직접 구현합니다. 참고 완성본은 첫 구현 뒤에 비교하세요.

## 실습 순서

1. npm ci와 npm run check를 실행해 의도된 실패를 봅니다.
2. 원시 배열을 바꾸지 않고 숫자 순서로 정렬하는 방법을 생각합니다. p50은 가운데 부근, p95는 대부분의 요청보다 느린 경계를 뜻해요. 이 실습은 올림 순위 방식을 사용합니다.
3. summarize를 구현하고 검사합니다. 빈 배열·음수·숫자가 아닌 값은 측정 결과로 받지 않습니다.
4. Docker Desktop을 켜고 npm run build와 npm run measure를 실행합니다. 일회용 DB와 Redis, 실제 API와 Worker를 만듭니다.
5. baseline→increase→hold→release의 동시 요청 수1→4→4→1을 비교합니다. 각 단계10건, 새 계정으로3회 반복해 총120건만 보냅니다. 터미널 JSON을 파일로 저장하고 원시 배열과 요약을 같이 보관합니다.

## 설명3개

1. 평균만 보면 놓칠 수 있는 느린 요청을 p95로 설명하세요.
2. API의 CPU와 Worker의 CPU를 따로 기록하는 이유는 무엇인가요?
3. 메모리가 늘었다는 한 번의 관찰만으로 메모리 누수라고 말할 수 있나요?
