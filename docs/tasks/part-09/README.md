# 9단계 — 서버가 바쁠 때 어디서 기다리는지 찾기 (3주)

이번에는 진짜 서버·DB·채팅 연결을 사용합니다. **조건을 적고 실행해서, 가장 오래 걸리는 곳을 증거로 찾는 연습**입니다. 내 컴퓨터 안의 전용 실습 환경만 사용합니다. 다른 서비스 주소를 넣는 기능은 없습니다.

[쉬운 설명](lesson.md) → 예상 → A/B/C 구현 → 실제 실험 → [해설](explanation.md) → 독립 변경 순으로 진행하세요. 학습자는 여전히 0단계·미시작입니다.

## 먼저 예상하기

1. 8명이 접속했는데 1명만 초당 2개를 보내면 발송 수와 전달 수는 같을까요?
2. 99번은 10ms, 1번은 2초 걸렸다면 평균만 적어도 괜찮을까요?
3. 수신자 권한 확인을 한 명씩 하는 것과 4명씩 하는 것에는 어떤 장단점이 있을까요?

## A주 — 숫자를 올바르게 계산하기

1. A: 지연 시간을 작은 순서로 정렬합니다. 원본 배열은 바꾸지 않습니다. p95는 `ceil(개수×0.95)`번째 값입니다. 빈 배열은 null이며 없는 값을 0ms라고 쓰지 않습니다.
2. 음수·NaN·Infinity·문자열 표본은 잘못된 측정이므로 거부합니다.
3. B: clients 1~10, rooms 1~2, senders 1~clients, 각 발송자의 rate 1~5/초, seconds 1~60, ASCII bytes 1~500을 허용합니다. 모든 값은 정수이고 다른 키는 거부합니다.
4. 공개 검사에서 작은 배열부터 확인합니다. 표본이 2개일 때의 p99와 1만 개일 때의 p99가 얼마나 다른 의미인지 적습니다.

## B주 — 같은 실험을 낮게·높게·다시 낮게

| 구간 | 접속/방/발송자 | 발송자당 빈도 | 시간 | 글 크기 |
| --- | --- | --- | --- | --- |
| 기준 | 2 / 1 / 1 | 1개/초 | 2초 | ASCII 128바이트 |
| 증가 | 4 / 2 / 2 | 2개/초 | 3초 | 동일 |
| 유지 | 8 / 2 / 4 | 2개/초 | 4초 | 동일 |
| 해제 뒤 | 2 / 1 / 1 | 1개/초 | 2초 | 동일 |

이 시간은 빠른 재현을 위한 기본 실험이며 장시간 운영 검증이 아닙니다. README만으로 처음 해 보는 작은 실험입니다. 오래 측정하려면 실험 정의와 중단 조건을 먼저 기록하고 같은 조건으로 반복합니다.

한 발송자는 앞 응답을 기다린 뒤 다음을 보냅니다. 서버가 느려져도 밀린 요청을 끝없이 쌓지 않습니다. 그래서 설정한 빈도와 실제 성공 빈도가 달라질 수 있습니다. 원시 시각·왕복 지연·성공/실패·전달/중복 수·서버 CPU/RSS·DB probe를 모두 읽습니다.

중단 기준: 서버 RSS 256MiB 초과, 10번 이상 시도한 뒤 오류율 20% 초과, 최근 왕복 1.5초 초과. 각 ack 제한은 2초입니다. 초과하면 중단 사실을 남기고 성공 결과로 처리하지 않습니다. API 최대 연결 20·이벤트 10회/초·동시 대기 4개라는 선수 제한도 그대로입니다.

## C주 — 하나 바꾸고 같은 조건으로 다시 보기

수신자 세션과 회원권을 한 명씩 확인하면 수신자가 늘수록 왕복이 늘어납니다. C는 4명씩 한 묶음으로 확인하되 **모든 검사를 마친 뒤** 다음 묶음을 시작합니다. Promise.allSettled를 조사하세요. 한 검사가 실패했다고 나머지 진행 중 작업을 방치해서는 안 됩니다. 권한 검사를 지워서 빠르게 만드는 것은 개선이 아닙니다.

1명씩과 4명씩의 코드·설정 차이는 이 부분 하나입니다. 같은 기기·데이터 초기 상태·메시지·방·빈도·시간으로 재실행합니다. 실행 순서도 번갈아 순서 영향을 줄입니다. p95가 줄지 않았다면 그대로 적고 원인을 다시 조사합니다.

서버는 별도 자식 프로세스여서 CPU·RSS를 따로 읽지만 발생기와 같은 기기입니다. CPU 경쟁·로컬 네트워크·작은 표본의 한계가 있습니다. SELECT 1 probe는 DB 접근 지연의 참고값이며 메시지 저장 SQL의 실행 시간 자체는 아닙니다. 이 실험 결과를 실제 서비스의 최대 시청자 수로 바꾸어 말하지 않습니다.

## 설명 3개와 독립 변경

1. ack 지연과 모든 수신자의 표시 완료가 왜 같지 않은지 설명하세요.
2. 개선 뒤에도 남겨 둔 인증·회원권 검사와 동시 실행 상한을 코드에서 찾으세요.
3. 원시 결과로 내 병목 가설을 지지하거나 반박해 보세요. 서버·DB·발생기 중 판단 못 한 범위도 적습니다.

독립 변경: **오류율이 두 구간 연속 기준을 넘었을 때 중단하도록 바꾸되, 메모리·단일 지연 상한은 즉시 중단**하는 정책을 구현하세요. ‘구간’과 분모가 0일 때의 처리부터 정의합니다. 공개 원본의 중단 검사를 없애기만 하면 안 됩니다. 답은 제공하지 않습니다.
