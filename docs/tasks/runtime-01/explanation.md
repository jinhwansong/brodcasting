# 첫 구현 뒤 비교하는 해설

먼저 예상과 첫 시도를 남기세요. A는 0부터 count-1을 포함하는 반복문이며 i%97을 누적합니다. 97개 한 묶음의 합은 0+…+96=4,656입니다. 이것을 이용해 작은 기대값을 독립적으로 확인할 수 있습니다.

B의 중요한 점은 ‘async라는 단어’가 아니라 **실제로 다음 이벤트 루프 차례를 기다리는가**입니다. setImmediate의 Promise 버전을 기다리거나 직접 Promise로 감싸는 방법을 사용할 수 있습니다. 마지막 범위는 count를 넘지 않아야 합니다. 결과 수치와 콜백 순서 검사가 각각 다른 결함을 잡습니다.

실행기는 스레드와 프로세스에서 받은 메시지만 보고 바로 성공하지 않고 실제 종료까지 기다립니다. 오류·비정상 종료·10초 제한은 실패로 남습니다. 이 상한은 자식의 끝나지 않는 실행을 방치하지 않기 위한 것입니다. CLI에는 사용자 임의 파일·쉘·외부 서버 주소를 받지 않습니다.

새 작업마다 스레드를 띄우는 이번 방식은 시작 비용을 관찰하기 위한 실험입니다. 실서비스에서 매 알림마다 새 스레드를 만들라는 권장이 아닙니다. 다음 큐 과정의 Worker는 오래 살아 있는 별도 프로세스입니다. Node Worker thread와 BullMQ Worker의 ‘Worker’라는 이름이 같아도 실행 구조는 같지 않습니다.

reference-solutions/runtime-01은 비교 자료입니다. 독립 변경의 답은 여기에 포함하지 않습니다.
