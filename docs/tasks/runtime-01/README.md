# 알림 과정 1주 — 한 사람의 책상, 옆자리, 다른 사무실

이번 주는 알림을 보내기 전에 **어디서 일을 시킬지** 배웁니다. [쉬운 설명](lesson.md)을 먼저 읽으세요. 서버·DB·Redis·그래픽카드는 필요 없습니다. Node만 사용합니다.

## 먼저 예상하기

1. 긴 계산에 async를 붙이면 다른 CPU가 계산할까요?
2. 작은 계산 여러 번 사이에 쉬면 전체 계산은 빨라질까요, 다른 일의 차례가 빨라질까요?
3. 다른 프로세스에서 객체를 바꾸면 원래 객체도 바뀔까요?

정답을 찾기 전에 예상 세 문장을 [제출 양식](submission.md)에 적습니다.

과제 A는 i=0부터 count-1까지 **i를 97로 나눈 나머지**를 모두 더합니다. count가 1,000이면 답은 46,995입니다. 입력 범위 검사와 자식 생성은 제공합니다. 과제 B는 같은 합을 10,000개씩 계산하고 다음 묶음 전에 setImmediate로 실행권을 양보합니다. 마지막 남은 작은 묶음을 빠뜨리지 않습니다.

## 한 번에 한 단계씩

루트 README의 Node 준비 뒤, 저장소 루트에서:

```sh
npm run check:runtime-01
npm run experiment:runtime-01 -- 1000000
```

시작 코드는 15개 중 8개 통과·7개 의도된 실패입니다. 계산을 0으로 돌려주기 때문입니다. 모듈을 못 찾거나 자식을 시작하지 못한 오류는 과제 실패로 넘기지 않습니다.

1. A만 구현하고 검사합니다. 공개 기대값과 다른 합이 나오면 반복문의 시작·끝을 종이에 써 봅니다.
2. B를 구현합니다. Promise.resolve만 기다리면 setImmediate 차례를 계속 미룰 수 있습니다. [공식 이벤트 루프 설명](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)을 확인하세요.
3. 실험 JSON의 result가 다섯 방식에서 같은지 확인합니다.
4. order에서 probe는 예약한 작은 콜백, result는 계산 완료입니다. main/promise와 cooperative의 순서 차이를 설명합니다.
5. thread/process의 pid와 threadId, memory의 객체 값, exits의 7을 확인합니다. PID는 실행할 때마다 바뀌므로 외우지 않습니다.

count는 1,000~5,000,000 정수 하나만 받습니다. 기본은 1,000,000이며 세 번 반복합니다. 외부 주소나 무제한 반복 인수는 없습니다. 이 정도 계산은 빠르게 끝나므로 ms의 작은 차이에 큰 의미를 붙이지 않습니다.

## 설명 세 가지

1. Promise로 감싼 CPU 계산은 왜 다른 스레드가 계산한 것이 아닌가요?
2. 전체 작업 시간과 다른 콜백이 실행되기까지 걸린 시간은 왜 다른가요?
3. 일반 객체 복사·공유 버퍼·별도 프로세스의 메모리를 각각 설명하세요. 스레드 종료가 모든 충돌 격리를 뜻하지 않는 이유도 적습니다.

## 완성본을 가리고 독립 변경

**실행권을 양보하는 묶음 크기를 1,000/10,000/100,000 중 고를 수 있게 바꾸세요.** 잘못된 선택은 거부하고, 같은 합·다른 콜백 순서·전체 시간의 차이를 직접 기록합니다. 공개 검사는 원래 계약을 검사하므로 새 선택의 검사는 직접 추가합니다. 이 변경의 정답은 제공하지 않습니다.

[해설](explanation.md)은 첫 시도 뒤에만 읽습니다. [제작 검증](../../verification/runtime-01.md)은 제작자의 기록이며 학습자가 통과한 기록이 아닙니다. 현재 학습 상태는 0·미시작입니다.
