# 7단계 — 글이 많아져도 편하게 읽기 (3주)

채팅이 10개일 때는 괜찮던 화면이 1만 개에서는 느려질 수 있습니다. 이번에는 **왜 느린지 찾고, 읽던 자리를 지키며 고치는 연습**을 합니다. 서버는 켜지 않아도 됩니다. 이 실험의 글은 내 브라우저 안에서만 생기는 가짜 글입니다.

처음 배우는 사람은 [쉬운 설명](lesson.md)을 먼저 읽으세요. 핵심 답은 없는 설명입니다. 코드의 답을 다루는 [해설](explanation.md)은 첫 구현 뒤에 읽습니다. 학습 상태는 여전히 0단계·미시작입니다.

## 시작 전에 예상하기

[제출 양식](submission.md)에 짧게 적습니다. 틀려도 괜찮습니다.

1. 글 1,000개를 저장했는데 화면에는 14개만 그리면 나머지는 어디에 있을까요?
2. 위쪽 글을 읽고 있는데 새 글이 오면 화면을 맨 아래로 옮겨도 될까요?
3. 초당 500개를 60초 만들면 총 몇 개일까요? 그걸 모두 보관할 필요가 있을까요?

## 실행하고 파일 찾기

저장소 루트에서 실행합니다. Node 설치·처음의 `npm ci`는 루트 README를 따릅니다.

```sh
npm run dev:part-07
```

http://127.0.0.1:5187 을 엽니다. ‘7단계 · 브라우저 실험실’과 빈 채팅 목록이 보입니다. 처음에는 TODO 때문에 검사와 재생이 완성되지 않은 상태입니다.

| 순서 | 내가 고칠 파일 (labs/part-07/src/ 아래) | 할 일 |
| --- | --- | --- |
| A | window.ts의 retain | 최근 1,000개만 남기기. 받은 배열은 바꾸지 않기 |
| B | window.ts의 range | 스크롤 위치에서 보이는 8줄과 앞뒤 3줄의 번호 구하기 |
| C | useReplay.ts | 글 생성·묶음 갱신·대기 상한·타이머 정리 |
| 제공 | App.tsx, Timeline.tsx, styles.css | 방 선택·읽던 위치·입력 연습·화면 골격 |

공개 검사 코드는 checks/part-07/에 있습니다. reference-solutions/part-07/은 제작자 비교용 완성본입니다. 첫 시도 전에 열거나 복사하지 않습니다.

## A주 — 보관하는 글과 그리는 글

1. 종이에 1~10을 적습니다. 최대 6개만 보관한다면 새 글 11, 12 뒤에 무엇이 남을지 적습니다.
2. A를 작성합니다. 이번 실제 상한은 1,000개입니다. `slice`가 원본을 바꾸는지 공식 문서로 확인합니다.
3. B를 작성합니다. 한 줄 높이는 48px, 화면 높이는 384px입니다. 화면 밖의 앞뒤 3줄도 그립니다. 끝 범위는 포함하지 않습니다.
4. `npm run check:part-07`을 실행합니다. A/B 검사가 먼저 통과하는지 봅니다. C의 재생 검사는 아직 실패할 수 있습니다.

## B주 — 자주 오는 글을 묶기

1. C에서 100ms마다 속도/10개를 만듭니다. 속도는 제공 선택지 10/100/500개/초입니다. 일정 시간이 지났다고 밀린 1만 개를 한꺼번에 만들지 않습니다.
2. 별도 100ms 타이머로 대기 글을 한 묶음씩 화면 상태에 넣습니다. 대기는 최근 200개만 남기고 생략한 수를 표시합니다.
3. 시작할 때 60초 뒤 중단하도록 예약합니다. 중지·방 전환·화면 종료 때 생성/반영/중단 타이머를 모두 지웁니다. 다시 켤 때 두 배 속도가 되지 않아야 합니다.
4. 낮은 속도부터 재생합니다. 입력칸에 글을 써 봅니다. 목록 위쪽으로 올라간 뒤 새 글 버튼으로만 최신 위치로 이동해 봅니다.

보관 상한 밖으로 밀린 옛 글은 이 화면에서 읽을 수 없습니다. 안내를 확인하세요. 원본 DB를 지운 것은 아닙니다. 실제 채팅 이력 조회는 6단계의 별도 책임입니다.

## C주 — 같은 조건으로 비교하기

```sh
npm run typecheck:part-07
npm run build:part-07
npm run check:part-07
npm run preview:part-07
```

마지막 명령은 빌드한 화면을 http://127.0.0.1:4287 에서 엽니다. 개발 화면과 빌드 화면의 수치를 섞지 않습니다.

‘보관한 글 모두 그리기’와 ‘보이는 부분만 그리기’를 같은 기기·브라우저·속도·60초로 각각 3번 비교하세요. 전체 그리기도 보관 상한은 1,000개입니다. [측정 양식](browser-checklist.md)에 Performance 기록·입력 반응·메시지 DOM 수·Memory 추이를 남깁니다. 실제 측정 전에는 빈칸입니다. 자동 검사의 jsdom 실행 시간은 브라우저 성능 점수가 아닙니다.

## 설명 질문 3개

1. 보관 1,000개인데 화면이 14개일 수 있는 이유를 코드 두 곳으로 설명하세요.
2. 방을 바꾸면 타이머가 어디서 사라지나요? 사라지지 않았다는 증거는 어떻게 찾을까요?
3. 읽던 글이 보관 범위를 벗어났을 때 어떤 선택을 했나요? 불편함과 한계도 적으세요.
