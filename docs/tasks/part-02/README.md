# 2단계 — HTTP API와 느린 응답

3주, 주당 6~8시간을 권장합니다. 메모리 데이터를 반환하는 NestJS 서버를 React 화면과 연결하고, 이전 응답이 최신 화면을 덮지 않도록 만듭니다. 요청·응답·상태 코드·런타임 검증·취소·캐시의 기본 경계를 설명하는 과정입니다. DB는 3단계, 인증은 4단계입니다.

## 먼저 예상하기

1단계의 목록·상세·공유 상태·포커스를 설명하고 독립 변경까지 해본 뒤 시작하세요. 이번에는 그 완료된 UI를 선수 기능으로 제공합니다. 참고 완성본을 보기 전에 [제출 양식](submission.md)에 적으세요.

1. 검색 `r` 요청 뒤 `re` 요청을 보냈는데 `re`가 먼저 끝나면 어떤 결과를 표시해야 할까요?
2. TypeScript에 `search?: string`을 적은 서버로 숫자·null·배열을 보내면 실행 중에도 자동으로 거부될까요?
3. 클라이언트가 abort하면 서버의 대기·DB·큐 작업도 반드시 중단될까요? 지금 구현된 범위와 미래 작업을 나눠 예상하세요.

## 두 터미널로 실행

Node.js 24.x 24.15.0 이상을 권장합니다(제작 검증 24.19.0). 저장소 루트에서 `npm ci` 후:

```sh
# 터미널 1 — 로컬 API, 127.0.0.1:3002
npm run dev:part-02:api
```

```sh
# 터미널 2 — 화면, 터미널에 표시된 Vite 주소
npm run dev:part-02
```

서버 명령은 한 번 빌드하고 실행합니다. 서버 소스를 수정하면 중지 후 다시 실행하세요. client의 `/api` 요청은 Vite 개발 프록시가 API로 보냅니다. 서버 PORT를 바꿨다면 client의 프록시 대상도 맞춰야 합니다. 루트의 기본 `npm run dev`, `npm test`는 계속 0단계입니다.

```sh
npm run typecheck:part-02
npm run build:part-02
npm run check:part-02
```

서버만 검사하려면 `npm run check:part-02:api`, client만 검사하려면 `node checks/part-02/run.mjs exercise client`를 사용합니다. 시작 코드 타입 검사·빌드는 성공하고 행동 검증은 의도적으로 실패합니다. 초기 총 개수와 실제 실패는 [제작 기록](../../verification/part-02.md)을 확인하세요. 구문·모듈 오류를 과제의 정상 실패로 간주하지 않습니다.

## 직접 채울 곳

| 과제 | 파일 | 맡은 책임 |
| --- | --- | --- |
| A | `labs/part-02/server/src/broadcast.service.ts` | 메모리 목록 검색·정렬·상세·지연·실패 |
| B | `server/src/broadcast.dto.ts`, `raw-input-keys.pipe.ts`, `create-app.ts` | 변환 전 입력 키 검사·DTO 값 검증·전역 Pipe 순서 |
| C | `labs/part-02/client/src/api.ts` | URL 인코딩·fetch·HTTP 실패·JSON 구조·AbortSignal |
| D | `client/src/useLatestRequest.ts` | 로딩·최신 요청 반영·오류·재시도·정리 |
| 제공 | Module·Controller·부트스트랩·fixtures | 기동·DI·라우트·파서 크기 제한·캐시 헤더의 골격 |
| 선수 UI | App·목록·상세·펼침 영역·체류 타이머·CSS | 1단계 기능과 stable loader 연결. 영상·인증·DB 없음 |

Module은 controller/provider를 묶고, Controller는 HTTP 입력과 서비스 호출을 연결하며, Service는 조회 규칙을 수행합니다. 제공된 DI 연결을 코드 위치로 추적하세요. 검증을 위해 서버는 tsc가 만든 decorator metadata를 포함한 ESM 빌드를 실행합니다. 새 Nest CLI나 전역 패키지를 설치할 필요가 없습니다.

## API 계약

| 요청 | 성공 | 실패 |
| --- | --- | --- |
| `GET /api/broadcasts` | 200 `{items: Broadcast[]}` | 잘못된 조건 400, 오류 실험 503 |
| `GET /api/broadcasts/:id` | 200 `Broadcast` | 잘못된 id/조건 400, 없는 id 404, 오류 실험 503 |
| `POST /api/search-preview` | 200 `{items}`. 조회만 하고 저장하지 않는 JSON 입력 실험 | 타입/미정의 필드 400, 잘못된 JSON 400, 본문 8kb 초과 413 |

- 목록의 선택적 필드는 search(문자열, 최대 80자), sort(`viewers-desc` 또는 `title-asc`), scenario(`normal`/`slow`/`error`)입니다. 빠진 값은 빈 검색·시청자 순·정상 실험으로 취급합니다. 선택적이라는 이유로 null을 허용하지 않습니다.
- 상세 query에는 scenario만 허용합니다. id는 소문자 영숫자·하이픈 1~32자이며 공백·개행·초과 길이는 거부합니다.
- 검색은 공백을 trim하고 제목 또는 진행자를 대소문자 무시 부분 일치로 찾습니다. 정렬 동률이면 id 오름차순입니다. 원본 배열·객체를 바꾸지 않습니다.
- 알려지지 않은 필드, 중복 query로 들어온 배열, JSON의 숫자·객체·배열을 서버에서 거부합니다. `constructor`, `toString`, `prototype`, `hasOwnProperty`, `__proto__`도 허용 필드가 아닙니다. DTO 변환이 일부 키를 지울 수 있으므로 변환 전 원래 입력의 own key를 허용 목록과 비교한 다음 DTO 값 검증을 실행합니다. 프론트의 maxLength나 select 선택지만 믿지 않습니다.
- 성공·오류 응답은 Cache-Control: no-store입니다. 클라이언트 fetch도 이번 실습에서는 no-store를 사용합니다.
- normal은 인위적 대기 없음. slow는 trim한 검색 길이 0~1일 때 450ms, 2 이상일 때 30ms 대기합니다. 상세 slow는 450ms입니다. error는 503입니다. 실제 운영에 노출하는 진단 기능이 아닙니다.

직접 요청을 먼저 예상하고 로컬에서 확인하세요. 다음 예시는 본인 컴퓨터의 실습 API만 사용합니다.

```sh
curl -i 'http://127.0.0.1:3002/api/broadcasts?search=React'
curl -i 'http://127.0.0.1:3002/api/broadcasts/missing'
curl -i 'http://127.0.0.1:3002/api/broadcasts?sort=unknown'
curl -i -X POST 'http://127.0.0.1:3002/api/search-preview' \
  -H 'Content-Type: application/json' --data '{"search":12}'
```

404는 HTTP 응답이 도착한 경우이고 서버 중단은 응답 자체를 받지 못한 경우입니다. `fetch`의 Promise 성공과 HTTP 성공을 구분하세요. JSON을 읽은 뒤에도 예상 구조인지 확인합니다.

## 최신 응답과 화면 계약

- 목록과 상세는 각각 로딩·성공·오류·재시도를 갖습니다. 빈 목록은 200의 빈 결과이며 오류 안내와 구분합니다.
- 검색/정렬/실험 변경으로 새 요청을 시작하면 이전 요청은 정리합니다. 이전 성공뿐 아니라 이전 실패도 최신 상태를 덮으면 안 됩니다.
- AbortController와 최신 여부 판단을 함께 다룹니다. 공개 검증은 취소를 무시한 Promise도 나중에 완료시켜 봅니다.
- 검색이 선택 방송을 목록에서 숨겨도 상세는 별도 id 요청으로 유지합니다. 목록 재시도는 상세의 선택·결과를 지우지 않습니다. 상세를 닫거나 다른 id를 선택하면 이전 상세 요청을 정리합니다.
- 목록·상세 즐겨찾기는 기존 로컬 상태를 공유합니다. 새로고침 뒤 저장은 이번 요구사항이 아닙니다.
- Hook에 전달하는 loader는 App의 useCallback으로 안정화되어 있습니다. 렌더 때마다 새 함수를 만들면 어떤 요청 반복이 생길지 설명하세요.

## 3주 진행과 증거

| 기간 | 작업 | 남길 증거 |
| --- | --- | --- |
| 1주 / 1~2시간 | 예측·실행·Module/Controller/Service와 DI 추적 | 한 요청의 코드 경로 |
| 1주 / 나머지 | A 목록·상세·404, B DTO·Pipe | 직접 HTTP 200/400/404/413/503과 정제된 응답 |
| 2주 / 2~3시간 | C URL·상태 코드·JSON·연결 실패 | 정상 응답과 형식/네트워크 실패 구분 |
| 2주 / 나머지 | D 응답 역전·취소·재시도 | 이전 성공/실패 무시와 정리의 자동 검증 |
| 3주 / 2~3시간 | 느린 응답·서버 중단·캐시 관찰 | 자동 HTTP 결과, 브라우저 Network 기록은 추후 |
| 3주 / 나머지 | 설명·독립 변경·재검증 | 본인 답변·timeout 변경·도움 범위 |

‘짧은 검색을 느리게’를 선택하고 `r` 다음 `re`를 빠르게 입력해 비교하세요. 완료 순서와 요청 순서가 달라도 최신 검색 결과가 남아야 합니다. 네트워크를 끊거나 API 터미널을 중지했을 때도 오류를 성공/빈 목록으로 숨기지 않습니다. 서버를 다시 시작한 뒤 같은 조건으로 복구합니다.

## 캐시를 구분하는 작은 실험

HTTP 응답의 no-store는 저장을 금지하는 정책이고, no-cache는 저장된 응답을 재사용하기 전 검증하도록 하는 정책입니다. React의 파생 값 계산·메모이제이션과 HTTP 캐시는 다른 위치에 있습니다. 이번 기본 구현은 결과 캐시가 없으므로 같은 조건 재시도도 요청을 보냅니다. 실제 브라우저의 cache/transfer 표시는 [후속 목록](browser-checklist.md)에서 확인하고 실행 전까지 기록을 만들지 않습니다.

## 설명 질문 3개

1. 하나의 검색 요청을 App → loader → fetch → Controller → DTO/Pipe → Service → JSON → Hook → 화면으로 따라가세요. Module과 DI는 어디에 관여하나요?
2. 두 요청의 응답 순서가 뒤집힐 때 이전 성공·실패를 어떻게 배제했나요? abort와 서버 작업 중단의 차이를 현재 서버 코드로 설명하세요.
3. 오류 하나를 골라 요청·상태 코드/네트워크·응답 내용·실제 원인·복구를 연결하세요. 타입 선언·입력 검증·본문 크기 제한·캐시 정책은 각각 어디서 작동하나요?

## 해설을 가리고 할 독립 변경

요청 시간 제한을 추가하세요. 기본 800ms, 실험용 100ms를 선택할 수 있게 하되 시간 초과·일반 HTTP 실패·이전 요청 취소의 표시 정책을 먼저 적습니다. slow의 450ms 요청을 100ms에서 중단하고, 정상 30ms 요청과 재시도를 처리해야 합니다. 성공·실패·조건 변경·닫기·언마운트 후 timeout 자원을 정리하세요. 가짜 시간과 제어 가능한 Promise로 경계와 이전 결과 무시 검증을 직접 추가하고 기존 회귀를 확인합니다. 이것은 기본 공개 검증에 포함되지 않습니다.

## 통과 판단

정상/빈 목록/404/입력 거부/서버 오류/연결 실패/응답 역전의 증거, 설명 3개, AI 완성 코드 없이 독립 변경, 도움 범위를 함께 검토합니다. 참고 완성본과 자동 테스트의 성공이 학습 완료를 뜻하지 않습니다. 실제 브라우저 확인은 사용자 요청에 따른 후속 미검증 항목으로 남깁니다.
