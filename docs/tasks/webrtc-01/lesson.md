# 쉬운 설명 — 파일을 트는 것과 내 화면을 보내는 것

## 택배 상자와 영상 통화

샘플 영상은 이미 만들어 둔 파일입니다. 브라우저가 그 파일을 받아 재생합니다. WebRTC는 지금 생기는 화면과 소리를 다른 브라우저로 보내는 기술입니다. **WebRTC 영상도 video 태그로 보여줄 수 있습니다. video 태그가 보인다고 무조건 녹화 파일인 것은 아닙니다.**

이번 사이트는 두 공간을 구분합니다. 기존 방송 목록은 ‘샘플 방송’입니다. ‘WebRTC 송출·시청 실습’ 버튼으로 들어간 곳에서는 실제 브라우저끼리 영상을 보냅니다.

## 서버는 소개를 하고, 브라우저끼리 영상을 보냅니다

1. 로그인한 송출자가 방을 만듭니다. 서버가 방 번호를 정합니다.
2. 시청자가 그 방을 선택합니다.
3. 두 브라우저가 ‘이런 영상과 연결 방법을 쓸 수 있어요’라는 설명을 서버를 통해 주고받습니다. 설명서 이름이 SDP입니다. 먼저 제안하는 것이 offer, 응답하는 것이 answer입니다.
4. 연결되면 영상 데이터는 두 브라우저 사이로 갑니다. 이번 구조의 Node 서버가 영상을 받아 변환하거나 저장하지 않습니다.

연결 후보를 찾는 과정을 ICE라고 부릅니다. 이 실습은 후보 수집이 끝난 뒤 SDP를 한 번에 보냅니다. 끝나지 않으면8초 뒤 멈추고, 사용자가 종료해도 기다림을 취소합니다. 기다리던 타이머와 이벤트를 남기면 이미 종료한 방송이 뒤늦게 살아날 수 있습니다.

서버는 아무 주소로 설명서를 전달하지 않습니다. **같은 방의 송출자와 시청자 사이에서만** 전달합니다. 브라우저가 보낸 userId를 믿지 않고 실제 로그인 세션을 확인합니다. 로그아웃한 연결은 다시 검사해서 끊습니다.

## 먼저 두 탭으로 연습하기

1. 사이트와 API를 켠 뒤 `http://127.0.0.1:5190`에 접속합니다. 가입·로그인하고 WebRTC 실습실로 갑니다. 실습방 생성에는 기존 r1 관리자 권한이 필요하지 않습니다.
2. 방송 제목을 정하고 ‘움직이는 테스트 화면 송출’을 누릅니다. 카메라·마이크 권한을 요청하지 않는 직접 그린 화면입니다. 숫자와 사각형이 움직여야 합니다.
3. 표시된 방 주소를 다른 탭에 엽니다. 같은 브라우저의 탭은 로그인 쿠키를 공유합니다. 열린 실습 방송에서 ‘이 방송 시청’을 누릅니다.
4. 시청 탭의 사각형이 움직이고 ‘처리한 영상 프레임’과 ‘영상 데이터’가 늘어나는지 확인합니다. 이 숫자는 getStats()의 실제 값입니다. 지연 시간이 몇 ms라는 뜻은 아닙니다.
5. 시청 탭을 새로고침합니다. 송출 탭의 시청자가 줄고 다시 시청 버튼으로 접속할 수 있어야 합니다.
6. 송출 탭에서 ‘송출·시청 종료’를 누릅니다. 시청 탭에 종료 안내가 뜨고 방 목록에서 사라져야 합니다.
7. 다시 송출·시청한 뒤 한 탭에서 로그아웃합니다. 같은 세션을 쓰던 다른 탭도 영상 연결이 끊겨야 합니다. 새로 로그인한 뒤 다시 시작합니다.

카메라 송출은 브라우저에서 내가 카메라 권한을 허용할 때만 시작합니다. 마이크 체크는 기본으로 꺼져 있습니다. 화면 공유는 내가 고른 창·화면만 보내고 소리는 보내지 않습니다. 비밀번호 창이나 개인 대화가 보이는 화면을 고르지 마세요. 공유를 끝낼 때 트랙도 정지하고 연결도 닫습니다. 브라우저의 공유 종료 버튼으로 끝내도 앱이 정리합니다.

## 다른 PC에서 연습하려면

`127.0.0.1`은 **지금 접속한 그 PC 자신**입니다. 다른 PC에 이 주소를 보내면 서버 PC에 연결되지 않습니다. 같은 공유기의 사설 IP와 신뢰되는 HTTPS가 필요합니다. 일반 HTTP의 사설 IP 주소에서는 카메라·화면 공유가 제한됩니다. 같은 공유기를 써도 게스트 Wi-Fi 격리나 방화벽 때문에 연결되지 않을 수 있습니다.

아래는 서버 PC의 주소가192.168.0.10일 때의 예입니다. 실제 자신의 주소로 바꿉니다. 해당 IP가 인증서의 SAN에 포함되고, 두 PC의 브라우저가 그 인증서 발급자를 신뢰해야 합니다. 인증서와 개인 키는 자신의 로컬 폴더에 두고 Git에 넣지 않습니다. **인증서 경고를 무시해서 통과시키지 않습니다.** 인증서 신뢰 설정은 PC 소유자가 직접 확인합니다.

서버의 `.env`에는 다음 UI 출처를 정확히 지정합니다.

```text
PART06_BROWSER_ORIGIN=https://192.168.0.10:5190
```

API 터미널에서 `.env`를 적용해 `npm run dev:api`를 실행합니다. UI를 켜는 다른 PowerShell 터미널에서 다음을 설정합니다. 경로는 예시입니다.

```powershell
$env:BROADCAST_LAN_HOST='192.168.0.10'
$env:BROADCAST_HTTPS_CERT='C:\local-certs\broadcast-cert.pem'
$env:BROADCAST_HTTPS_KEY='C:\local-certs\broadcast-key.pem'
npm run dev
```

두 번째 PC에서 `https://192.168.0.10:5190`으로 접속하고 자기 실습 계정으로 로그인합니다. 방 주소도 이 HTTPS 주소로 공유합니다. 기본 설정은127.0.0.1이고, LAN 설정은 내가 위 변수를 지정한 때만 켜집니다. API와 DB는 계속 loopback에 둡니다. 방화벽·포트포워딩·공개 배포는 이 명령으로 자동 변경하지 않습니다.

이 실습에는 외부 STUN·TURN 서버 설정이 없습니다. 그래서 서로 다른 인터넷 회선에서는 연결되지 않을 수 있습니다. TURN은 직접 연결이 안 될 때 영상을 대신 전달하는 중계 서버입니다. 이번 검증은 같은 PC의 두 탭에서 했으며 **물리 PC 두 대·카메라·신뢰 인증서 설정은 직접 확인할 항목**입니다.

## 시청자가 늘면 돈이 저절로 절약될까요?

이번 구조는 송출자가 각 시청자에게 따로 보냅니다. 같은 화질이라면 시청자가 네 명일 때 송출자의 업로드 부담도 대략 네 연결분이 됩니다. 방은5개, 방마다 시청자는4명, 전체 소켓은20개까지로 제한합니다. 큰 방송 서비스용 구조가 아닙니다.

전에 이야기한 ‘다른 시청자가 받은 영상 일부를 나눠 준다’는 방식은 시청자끼리 조각을 공유하는 P2P 전송 구조에 가깝습니다. 이번에는 시청자가 다른 시청자에게 영상을 재전송하지 않습니다. 실제 서비스가 어떤 방식을 쓰는지는 공식 자료 없이 단정하지 않습니다.

미니 PC에서 이번 Node·DB 서버만 실행한다면 영상 변환용 그래픽카드는 이 실습에 필요하지 않습니다. 영상 압축·해제는 송출·시청 브라우저 쪽에서 합니다. 나중에 서버에서 영상을 받아 여러 화질로 변환하는 기능을 추가하면 요구 사양을 다시 판단해야 합니다.
