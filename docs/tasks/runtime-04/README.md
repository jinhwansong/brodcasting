# 알림4주 — 다시 해도 한 번만 남기기

3주에는 큐에 일을 넣고 다시 시도했습니다. 이번에는 **같은 일이 다시 실행되어도 가짜 발송 기록은 한 번만 남기기**를 연습합니다. [쉬운 설명](lesson.md)부터 읽고 [빈 제출 양식](submission.md)에 예상부터 씁니다. 실제 이메일이나 휴대폰 알림은 보내지 않습니다.

## 먼저 예상하기

가짜 발송 기록을 DB에 저장한 직후, Worker가 ‘끝났다’는 대답을 하기 전에 오류가 났다고 생각해 보세요. 큐가 다시 시키면 발송 기록이 두 개가 될까요? Redis의 완료 기록을 지웠어도 중복을 알아볼 수 있을까요?

## 내가 고칠 곳

`labs/runtime-04/src/sender.ts`의 두 함수가 과제입니다. 입력 검사·Nest 시작·Redis 연결·DB 주소 제한·종료 정리는 선수 코드로 제공합니다. 3주의 failures 숫자 대신 이번 주는 **정확히 id와 mode 두 필드**를 받습니다. 이전 접수 본문을 그대로 쓰면400입니다.

| 과제 | 해야 할 일 |
| --- | --- |
| A deliver | 같은 DB client에서 BEGIN→영수증 INSERT→가짜 발송 INSERT→COMMIT. 실패하면 ROLLBACK. 같은 ID는 mode도 비교 |
| B processDelivery | 아래 다섯 mode를 구분하고 A를 호출. 영구 실패에는 UnrecoverableError 사용 |

| mode | 실습에서 일어날 일 |
| --- | --- |
| normal | 바로 DB 저장 |
| transient | 첫 두 시도는 실패, 세 번째 시도에 저장 |
| permanent | 다시 해도 안 되는 가짜 오류. 첫 시도에 최종 실패 |
| after-commit | 처음 DB 저장은 성공한 뒤 오류. 재시도는 기존 영수증을 사용 |
| slow | 500ms 기다린 뒤 저장. 작업 중 종료를 관찰하기 위한 짧은 대기 |

## 직접 해보기

Node engines에 맞는 Node와 Docker Desktop의 Linux 엔진을 준비합니다. 루트에서 `npm ci` 후 실행합니다.

```sh
npm run typecheck:runtime-04
npm run build:runtime-04
npm run check:runtime-04
```

첫 실행은15개 중4통과·11의도된 실패입니다. ‘Docker를 못 찾음’, ‘모듈 없음’, ‘DB 준비 실패’는 과제의 실패가 아닙니다. 환경 문제부터 해결합니다. 테스트를 지우거나 통과 숫자를 고쳐 맞추지 마세요.

1. 예상과 이유를 적습니다. 처음부터 완성본을 읽지 않습니다.
2. A를 구현하고 같은 검사를 실행합니다. 영수증과 가짜 발송이 각각 한 행인지 확인합니다.
3. 가짜 발송 저장에만 실패하도록 만든 공개 검사를 봅니다. 영수증도0행이어야 합니다. ‘둘 중 하나만 저장됨’은 통과가 아닙니다.
4. B를 구현합니다. transient는3번, permanent는1번, after-commit은2번 시도해야 합니다.
5. 큐의 완료 기록을 지운 뒤 같은 ID를 실행하는 검사에서도 DB 발송은1행이어야 합니다.
6. 실제 Worker 프로세스가 처리 중인 slow 작업을 마친 뒤 종료하는 검사를 확인합니다. API는 계속 응답해야 합니다.
7. [해설](explanation.md)을 비교하고 아래 설명과 독립 변경을 제출합니다.

검사기는 매번 **별도 PostgreSQL18.6·Redis8.6.7 컨테이너**와 제한된 runtime04_app 역할을 만듭니다. loopback 임의 포트·임의 비밀번호·고유 큐만 사용하고 끝나면 소유한 컨테이너를 정리합니다. 자동 실습 DB는 버려지므로 다음 검사 실행까지 영수증이 남지는 않습니다. 한 검사 실행 안에서 Redis 기록 제거와 Worker 종료를 재현합니다.

수동으로 API/Worker를 실행한다면 `schema.sql`을 적용한 **별도 실습 DB**와 SELECT/INSERT만 허용한 runtime04_app 역할을 먼저 준비합니다. DB는 brodcasting_runtime04_lab, host는127.0.0.1이어야 합니다. `RUNTIME04_DATABASE_URL`·`RUNTIME04_REDIS_URL`·`RUNTIME04_QUEUE_PREFIX`를 두 터미널에 설정한 뒤 각각 `node labs/runtime-04/dist/api.js`와 `node labs/runtime-04/dist/worker.js`를 실행합니다. API 기본 포트3014, 접수는 `POST /jobs`의 `{"id":"n-0123456789abcdef","mode":"after-commit"}`, 조회는 `GET /jobs/n-0123456789abcdef`입니다. 비밀번호를 문서·커밋·공유 로그에 적지 않습니다. 수동 환경을 직접 만들기 어렵다면 제공된 자동 실습으로 시작하세요. 전체 환경을 함께 켜는 방법은7주에서 다룹니다.

## 설명 세 가지

1. 영수증과 가짜 발송을 왜 같은 client의 트랜잭션으로 묶나요?
2. jobId 기록과 DB의 고유 ID는 각각 언제 없어지며 무엇을 막나요?
3. 일시 실패·영구 실패·작업 중 정상 종료를 이번 검사 한 개씩으로 설명하세요.

독립 변경: **처리 결과 조회 명령**을 추가해 큐 완료 기록이 사라져도 영수증의 ID·mode·저장 시각을 확인하게 하세요. 존재하지 않는 ID와 잘못된 ID를 구분하고 본문/주소에 DB 비밀번호를 노출하지 않습니다. 정답은 제공하지 않습니다.

이 주의 API는 로그인 없는 로컬 가짜 작업 실험입니다. 사용자별 알림함은5주입니다. 가짜 발송은 DB 안의 기록이므로 같은 트랜잭션에 묶을 수 있습니다. 실제 이메일을 보내고 DB에 적는 일은 같은 DB 트랜잭션으로 묶이지 않습니다. 이번 결과를 외부 발송의 ‘무조건 딱 한 번’ 보장으로 바꾸지 마세요.
