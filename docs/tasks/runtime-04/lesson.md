# 쉬운 설명 — 일을 다시 시켜도 괜찮게 만들기

급식 담당자가 빵을 나눠 주고 명단에 체크한다고 생각해 보세요. 빵을 줬는데 체크하기 전에 담당자가 자리를 비우면, 다음 담당자는 같은 사람에게 또 줄 수 있습니다. ‘끝났다는 표시’와 ‘실제로 일어난 일’ 사이에 빈틈이 있기 때문입니다.

큐에서도 비슷합니다. Worker가 일을 마쳤어도 큐가 그 대답을 못 받으면 다시 시킬 수 있습니다. **다시 실행될 수 있다는 전제**로 작업을 만듭니다. ‘같은 일을 반복해도 최종 결과가 같다’를 멱등성이라고 부릅니다. 말은 어렵지만 이번에는 ‘같은 ID의 가짜 발송은 한 줄’이라고 이해하면 됩니다.

이번 가짜 발송기는 DB에 두 줄을 씁니다. delivery_receipts는 ‘이 ID를 처리했다’는 영수증이고, fake_deliveries는 가짜 발송 효과입니다. 둘을 하나의 트랜잭션으로 묶습니다. 둘 다 성공하면 COMMIT, 중간에 실패하면 ROLLBACK입니다. 단체 사진을 찍을 때 모두 함께 나오거나 사진 자체를 취소하는 것과 비슷합니다.

PostgreSQL의 PRIMARY KEY는 같은 ID를 두 행으로 저장하지 못하게 합니다. 먼저 영수증을 INSERT하고, 새 영수증을 넣은 경우에만 가짜 발송을 적습니다. 이미 영수증이 있다면 같은 내용인지 확인하고 기존 결과를 사용합니다. 동시에 네 번 불러도 DB의 고유 제약이 한 건을 결정합니다. 먼저 SELECT만 하고 나중에 INSERT하면 두 작업이 동시에 ‘아직 없다’고 생각할 수 있으므로 충분하지 않습니다.

같은 트랜잭션의 명령은 **같은 client**로 실행해야 합니다. pool.query를 각각 부르면 서로 다른 DB 연결에 명령이 갈 수 있습니다. BEGIN을 보낸 연결에서 INSERT·COMMIT/ROLLBACK까지 마친 뒤 client를 반납합니다.

실패도 종류가 있습니다. 잠깐 안 된 일은 횟수와 대기를 정해 다시 시도합니다. 입력 자체가 틀린 것처럼 다시 해도 안 되는 일은 바로 실패로 끝냅니다. 계속 실패하는 일을 무한히 붙잡으면 다른 작업이 밀립니다. 이번 mode들은 실제 수신처를 쓰지 않고 이런 상황을 재현하는 약속입니다.

종료할 때는 새 일을 받지 않고 지금 하던 일을 기다립니다. Worker.close가 기다린 뒤 Redis 연결과 DB pool을 닫습니다. 전원을 강제로 끄거나 종료 시간이 지나 강제 종료하면 같은 일이 다시 실행될 수 있습니다. 그래서 종료 정리와 멱등 처리를 함께 배웁니다. Windows IPC 종료 검사와 Linux SIGTERM 검사는 같은 실행 증거가 아닙니다.

이 실험의 가짜 발송은 DB 안에 있으므로 영수증과 함께 저장할 수 있습니다. 실제 이메일 서버는 바깥에 있습니다. 이메일은 갔는데 영수증을 저장하지 못하는 빈틈이 남습니다. 실제 서비스에서는 발송 업체의 멱등 키·결과 조회·재처리 정책도 살펴야 합니다. 외부 발송은 이번 필수 실습이 아닙니다.
