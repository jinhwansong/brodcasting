# 3단계 — PostgreSQL과 페이지네이션 설계

## 목적과 선택

원본 CURRICULUM.md의 3단계(3주)는 방송·즐겨찾기의 PostgreSQL 저장, 직접 SQL, 제약조건·인덱스·마이그레이션·페이지 경계를 배우는 강의다. SECURITY_CURRICULUM.md의 SQL 바인딩·정렬 허용 목록·최소 DB 권한을 함께 구현한다. 제작은 계속하되 학습 상태는 0단계·미시작이다. 사용자는 이후 계획·제작·검증·커밋·푸시를 중간 승인 없이 위임했다.

별도 labs/part-03/{server,client}, 공개 checks/part-03, 독립 reference-solutions/part-03를 만든다. 기존 2단계의 Nest·fetch·최신 요청 처리를 선수 기능으로 제공한다. 새 ORM 대신 pg의 파라미터 쿼리를 쓴다. OFFSET 방식은 페이지 번호와 비용을 직접 연결하기 쉬워 선택했다. cursor 방식은 동시 변경·깊은 페이지 한계를 설명한 뒤 독립 변경 과제로 남긴다. 메모리 DB나 SQLite 대체 검증은 PostgreSQL 계약을 증명하지 못하므로 실제 서버를 사용한다.

## 데이터·실행 경계

- PostgreSQL 18 계열, pg 8.23.1·@types/pg 8.23.1. Node 범위 ^22.22.2 || ^24.15.0 || >=26.0.0과 기존 React/Nest/도구 버전을 유지한다.
- demo_users(id text PK), broadcasts(id text PK, title·host_name·description text NOT NULL, viewer_count integer NOT NULL CHECK >=0), favorites(user_id·broadcast_id NOT NULL, 복합 PK, 각 FK). 방송 삭제 시 해당 즐겨찾기를 CASCADE 삭제한다.
- 모든 API는 서버가 정한 demo-user 한 명의 공유 로컬 연습이다. 외부 owner/user id를 받지 않는다. 사용자별 인증·권한은 4단계에서 완성한다. API는 127.0.0.1:3003, Vite /api 프록시를 쓴다.
- migrations/001-schema.sql과 002-index.sql, 버전·SHA256 기록 및 transaction/advisory lock 기반 실행기를 제공한다. 적용한 파일 변경은 거부하며 재실행은 0개다. 시작 코드에는 테이블·기본 PK와 도구 골격을 제공하고 CHECK·즐겨찾기 제약·보조 인덱스 및 조회/변경 SQL을 과제로 남긴다.
- operator와 app 역할을 분리한다. app은 broadcasts SELECT, favorites SELECT/INSERT/DELETE만 갖는다. schema·migration·seed·실험은 operator로 실행한다. 예제 비밀번호는 실제 비밀값이 아니며 실행 값은 환경변수로 받는다. 연결 문자열을 출력·커밋하지 않는다.
- Docker Compose는 로컬 DB 선택 실행을 위해 postgres:18.6, 127.0.0.1:5543, named volume으로 제공한다. 제작 환경의 UID mapping은 root만 허용해 native PostgreSQL 기동이 불가능했다. 별도 GitHub 검증 브랜치의 Actions PostgreSQL18.6 service로 실제 DB 검증을 수행한다. 로컬 Compose 실행 성공을 주장하지 않는다.

## HTTP 계약

- GET /api/broadcasts: search 문자열 최대80, sort viewers-desc|title-asc, limit 기본2·1..50, offset 기본0·0..100000, favoritesOnly 기본false·true|false. 미정의·중복·잘못된 값은400. 숫자는 십진 정수 표기만 허용한다.
- 반환 {items: Broadcast[], limit, offset, hasMore}. Broadcast는 2단계 필드와 favorite:boolean. LIMIT limit+1로 다음 유무를 계산하고 실제 반환은 limit 이하로 제한한다. 빈 페이지는200·빈 배열·hasMore false다.
- 검색은 trim 후 제목/진행자의 대소문자 무시 부분 일치이며 %, _, 역슬래시는 문자 그대로 찾는다. 값은 $n 바인딩한다. ORDER BY는 고정된 허용 목록 두 개에서만 선택한다. 시청자 내림차순·id 오름차순, 제목 COLLATE "C" 오름차순·id 오름차순으로 동률을 안정화한다.
- GET /api/broadcasts/:id는 형식 오류400·없는 id404. PUT/DELETE /api/favorites/:id는 각각 {id,favorite:true|false}, 같은 작업 재시도는200이며 중복 행을 만들지 않는다. 존재하지 않는 방송은404. 이 두 경로의 외부 query·비어 있지 않은 body는400이다.
- API의 DB 장애는 정제한503이며 SQL/접속정보를 body에 내보내지 않는다. 요청 검증 실패 후 DB 변경이 없어야 한다. HTTP 응답은 no-store, JSON 파서는8kb다.

## UI와 학습 과제

작은 목록 화면에서 검색·정렬·이전/다음 페이지·즐겨찾기만 보기·저장 상태·재시도를 제공한다. 조건을 바꾸면 offset0으로 돌아간다. 요청·이전 성공/실패 정리는 제공된 2단계 Hook으로 유지한다. 즐겨찾기는 서버 응답 이후 반영하고 새로고침/새 앱 인스턴스에도 DB에서 읽는다. 쓰기 실패는 목록과 기존 즐겨찾기를 그대로 두고 별도 오류로 표시한다. UI 제공 범위는 DB 과제에 집중하기 위한 선수 코드다.

과제 A는 제약과 인덱스, B는 바인딩된 목록/상세 SQL, C는 멱등 즐겨찾기 SQL, D는 실행 계획 해석·페이지 한계와 독립 변경이다. 정답은 별도 reference에만 둔다. 설명 3개와 제출 양식, 브라우저 후속 목록을 제공하며 자동 테스트만으로 학습 통과를 기록하지 않는다.

## 실제 검증과 실험

공개 runner는 테스트 전용 loopback DB 이름 brodcasting_part03_test만 허용하고 고유 schema/role을 만들어 해당 자원만 정리한다. 환경이 없으면 명시적으로 실패하며 skip·모의 DB로 성공하지 않는다. migrations 재실행·수정 거부·실패 rollback, CHECK/FK/복합유일성/CASCADE, 실제 SQL 주입 문자열·문자 검색·동률 페이지·빈 페이지·중복 동시 PUT·재시작 지속성·권한 거부·실제 HTTP를 검사한다. 클라이언트 대표 UI는 jsdom이며 브라우저 검증과 구분한다.

로컬 실험 CLI는 brodcasting_part03_lab만 허용하고 연결 세션의 임시 테이블만 사용한다. 1천·1만·10만 행에서 같은 정렬 조회의 첫/깊은 페이지를 인덱스 전후 EXPLAIN(ANALYZE,BUFFERS,FORMAT JSON)으로 기록하고 전체/한 페이지 JSON byte를 비교한다. 실제 버전·환경·원시 계획과 단일 실행의 한계를 남긴다. 무조건 인덱스가 빠르다는 assertion은 두지 않는다.

독립 설치·타입 검사·빌드·실제 DB·기존 강의 회귀·새 컨텍스트 최종 리뷰를 마친 뒤 최신 main SHA를 조건으로 게시하고 tree 일치를 확인한다. 브라우저·Docker·공개 배포·외부 부하·유료 인프라는 실행하지 않는다. BunkerWeb은 전체 과정 마지막에 유지한다.
