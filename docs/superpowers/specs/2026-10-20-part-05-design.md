# 5단계 WebSocket 채팅 — 제작 설계

## 목적과 범위

CURRICULUM.md의5단계3주를 제작한다. 기존 로그인·개인 즐겨찾기·방 공지 위에 인증한 사용자 채팅을 연결하고 Gateway/Service 책임·연결 수명·방 권한·입력·구독 정리를 설명한다. 기존 중간 승인 없는 제작 위임과 이번 ‘계속 작업’ 요청에 따라 설계·계획을 자체 검토하고 순차 실행한다. 학습0·미시작, 브라우저 보류를 유지한다.

4단계를 독립 part-05에 선수 코드로 복사하고 이름·DB·포트만 분리한다. 기존0~4단계를 바꾸거나 공유 런타임 계층을 만들지 않는다. 단일 NestJS 서버와 Socket.IO를 사용한다. 원시 WebSocket 직접 구현은 연결/ack/정리를 다시 만들어야 하고 Redis adapter는 이번 단일 서버 학습에 불필요하다. 메시지 DB 저장·이력·재연결 복구·자동 재시도는6단계, 측정·가상화는7단계다.

## 데이터·권한

4단계 테이블에 room_members(user_id uuid FK users CASCADE,room_id text FK rooms CASCADE,복합PK)를 추가한다. API 역할에는 SELECT만 추가하며 membership 생성·삭제는 operator만 한다. 신규 가입은 채팅 회원권을 자동 부여하지 않는다. operator `grant-member --username NAME --room r1|r2`를 제공한다. room_admins의 공지 편집 권한과 채팅 membership은 별개다.

연결은 로그인만 요구한다. 방 입장·발송·각 수신자 전달 전에는 DB membership을 다시 검사한다. 가입·URL·소켓 payload에 role/userId를 넣어도 주체가 되지 않는다. user/id/time은 서버가 정한다. 메시지는 DB에 저장하지 않는다.

## 연결·세션 계약

Nest IoAdapter의 allowRequest로 Origin이 정확히 browserOrigin인 upgrade만 허용한다. CORS만으로 WebSocket을 보호했다고 주장하지 않는다. Engine.IO에 기존 express-session middleware를 연결하고 namespace middleware에서 인증을 완료하기 전에는 이벤트를 받지 않는다. async handleConnection만 인증 gate로 쓰지 않는다.

연결 request의 sessionID는 공식 cookie middleware가 검증한다. 각 이벤트와 전달 때 이 SID로 PostgreSQL store를 새로 읽어 절대 수명·사용자 존재를 확인한다. handshake의 SessionData만 신뢰하거나 reload 실패를 모두 익명으로 숨기지 않는다. HTTP logout은 store를 폐기하므로 이후 시작한 이벤트/전달은 거부한다. 1초 주기의 단일 sweep은 유휴 연결의 세션/현재 방 권한을 확인해 폐기·만료는 disconnect, membership 제거는 방 퇴장+403 안내를 한다. sweep 중첩·종료 후 timer를 막는다.

이미 인증·인가를 마친 진행 중 전달을 취소하는 보장은 없다. 같은 socket의 입장/발송은 직렬 처리해 방 전환 경합을 막는다. DB 장애는503으로 정제하고 성공·단순 만료로 감추지 않는다. 송신자와 수신자의 세션이 다른 계정으로 바뀌면 이전 연결을 폐기한다.

## 이벤트 계약

| 방향·이름 | 내용 |
| --- | --- |
| client→room:join | 정확히 `{roomId:'r1'|'r2'}`. 기존 방을 떠난 뒤 권한 확인·새 방 입장. 실패 후 이전 구독 없음 |
| client→chat:send | 정확히 `{roomId,text}`. text 일반 Unicode1..500자·공백만 거부. 현재 입장 방과 일치해야 함 |
| server→chat:message | `{id:UUID,roomId,user:{id,username},text,sentAt:ISO}` |
| server→chat:error | `{code,message}`. 수신 경계·유휴 권한/세션 변경 안내 |

ack는 `{ok:true,data}` 또는 `{ok:false,code,message}`다. join data는 `{roomId}`, send data는 Message다. code400형식/미정의 키,401인증/만료,403회원권,409현재 방 불일치,429상한,503DB다. 연결 거부는 connect_error의 정제 code 또는 Engine transport 오류이며 세션·쿠키·SQL을 응답/로그로 내보내지 않는다.

Socket.IO maxHttpBufferSize8192bytes, 연결 최대20개, socket 이벤트10회/1초·동시에 대기4개, UI 보관100개로 실습 범위를 제한한다. 상한은 로컬 단일 프로세스 보호이며 운영 분산 제한/부하 측정을 완료했다고 주장하지 않는다. ack 성공은 휘발성 처리 수락이며 모든 수신/저장 보장이 아니다. 일부 전달 뒤 오류/ack 유실은 결과 불명이다.

## 화면과 학습 과제

4단계 AuthPanel·목록·공지를 유지하고 ChatPanel에 방 선택·연결 상태·일반 텍스트 메시지·라벨 있는 입력·전송·수동 다시 접속을 더한다. 로그인된 안정 상태에서만 연결한다. auto reconnection/재시도/오프라인 발송 버퍼를 사용하지 않는다. ack timeout3초 뒤 성공 표시·자동 재전송 없이 초안을 유지한다.

useChat effect는 계정epoch/방마다 socket과 동일 handler를 정리하고 이전 socket의 event/ack/finally를 무시한다. 기본 구현은 방 변경 시 이전 연결을 정리하고 새 연결로 입장한다. StrictMode 이중 실행·방 전환·로그아웃·unmount 후 연결·구독이 누적되지 않아야 한다. 같은 계정 만료 재로그인은 초안을 보존하고 다른 계정/명시적 logout은 지운다. 텍스트/서버응답 형식을 확인하고 수신 목록은100개로 제한한다.

A ChatService의 payload검증/DB회원권, B Gateway의 입장/발송, C useChat의 연결/구독 수명을 과제로 남긴다. starter는 컴파일 가능하지만 거부/미연결이어야 한다. 나머지 인증·SQL·transport wiring·UI는 선수 코드다.3주 예측·힌트·공식 자료·설명3개·빈 제출·브라우저 미실행 양식을 제공한다. 독립 변경은 ‘연결 한 개를 재사용해 방을 이동하되 이전 방 전달/늦은 ack가 남지 않게 하기’이며 정답을 제공하지 않는다.

## 검증과 자체 검토

실제 PG+HTTP 로그인 cookie와 socket.io-client로 익명/위조cookie/Origin/만료/로그아웃/DB장애·회원권·방분리·권한삭제 후 수신거부·방전환 경합·입력·server identity·제한·종료를 검사한다. jsdom은 실제 hook을 transport경계 fake로 검증하고 실제 wire/proxy 검증과 분리한다. source-only npm ci/typecheck/build·실제 API/proxy socket·종료·operator 정상/거부·로그 표식 부재, starter의 의도된 실패와0~4회귀를 실행한다. 측정하지 않은 수치·브라우저 결과를 기록하지 않는다.

공식 근거: [Nest Gateway lifecycle](https://docs.nestjs.com/websockets/gateways), [Socket.IO express-session](https://socket.io/how-to/use-with-express-session), [middleware](https://socket.io/docs/v4/middlewares/), [Origin/allowRequest](https://socket.io/docs/v4/handling-cors/), [React 정리](https://socket.io/how-to/use-with-react).
