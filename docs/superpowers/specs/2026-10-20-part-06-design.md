# 6단계 메시지 저장·재연결·복구 — 제작 설계

## 목적과 선택

CURRICULUM.md의6단계3주를 독립 part-06으로 제작한다. 학습자는0·미시작이며 기존 중간 승인 없는 계획·제작·검증·게시 위임을 따른다. brainstorming과 writing-plans의 설계/계획 자체 검토를 순차 수행한다. 브라우저·공개 배포는 보류한다.

5단계의 인증·회원권·socket 제한·UI를 선수 코드로 복사한다. 실제 PostgreSQL 저장과 재전송 중복 방지, 이력/실시간 중첩·복구 경계가 이번 과제다. Socket.IO 메모리 connection-state recovery만으로는 프로세스 재시작·DB 저장을 증명하지 못한다. 단순 bigserial offset은 먼저 번호를 받은 미커밋 행보다 뒤 번호가 먼저 커밋되어 복구 커서가 누락할 수 있다. 따라서 방별 counter 행을 트랜잭션으로 잠그고 순서 배정·저장을 커밋한 후 전달한다. Redis·브로커·분산 exactly-once는 추가하지 않는다.

## 저장과 권한

API3006/client5186/DB5546, 전용 brodcasting_part06_test/lab·part06_app·PART06_*·brodcasting.part06.sid를 사용한다. 기존 exact 의존성을 재사용한다. 원본0~5와 루트 기본8명령을 보존한다.

chat_room_counters(room_id FK rooms PK,value bigint>=0), chat_messages(room_id,seq bigint>0,id UUID UNIQUE,user_id FK users,username,text,client_message_id UUID,sent_at timestamptz)를 추가한다. PK(room_id,seq), UNIQUE(room_id,user_id,client_message_id), text1..500자/nonblank, 사용자명은 발송 당시 서버 값이다. API에는 messages SELECT/INSERT와 counter SELECT/INSERT/UPDATE(value)만 추가한다. UPDATE/DELETE messages·회원권 수정·DDL은 주지 않는다. 삭제된 사용자의 메시지는 FK CASCADE이며 counter는 감소하지 않는다.

발송 트랜잭션은 counter 생성 ON CONFLICT DO NOTHING→SELECT FOR UPDATE→현재 회원권 확인→같은 방/사용자/clientMessageId 조회→동일 text면 기존 행 반환/다른 text면409→counter 증가·행 INSERT→COMMIT이다. lock은 commit까지 유지한다. rollback은 행과 counter를 함께 되돌린다. 커밋된 행이 없으면 전달/성공 ack가 없다. 이미 승인된 진행 중 작업을 revoke/logout으로 소급 취소하지는 않는다. 동시 다른 방은 독립 순서다.

## 프로토콜과 복구 경계

기존 room:join ack는 유지한다. chat:send는 정확히 {roomId,text,clientMessageId:UUIDv4}, Message는 기존5필드에 seq(정규화된 bigint 십진 문자열),clientMessageId를 더한다. ID의 중복 방지 범위는 같은 사용자·같은 방이며 내용을 바꾼 재사용은409다. 인증 주체는 계속 현재 SID의 서버 사용자다.

chat:history는 정확히 {roomId,after} 또는 {roomId,after,until}. after/until은0..9223372036854775807의 정규 십진 문자열이다. 현재 입장·세션·회원권을 매번 검사한다. until 생략 시 DB의 현재 커밋 counter를 고정한다. after<=until<=현재 counter이며 위반은400/409로 정제한다. 응답은 {items,until,next,done}, seq>after AND seq<=until ORDER BY seq ASC LIMIT51로 조회하고 최대50개를 보낸다. 더 있으면 next=마지막 seq, 끝이면 next=until이다. 삭제된 행의 구멍도 끝까지 진전할 수 있다. 후속 페이지는 같은 until을 보낸다.

실시간 chat:message와 발송 ack는 저장 행을 알려주지만 복구 cursor를 직접 진전시키지 않는다. client는 이를 이력 재확인의 신호로 사용한다. 따라서 늦은 낮은 seq의 실시간 이벤트·이력과 겹치는 행·다른 socket의 동시 발송이 cursor를 건너뛰지 않는다. 연결/입장 직후부터 신호를 받아 단일 직렬 이력 pump를 dirty로 표시하고, 한 snapshot 완료 후 dirty면 새 watermark로 조회한다. DB만 커밋되고 서버가 전달 전에 중단된 경우는 재연결/수동 복구 때 회수한다. 온라인 상태에서 모든 commit을 즉시 감지하는 보장은 없다.

각 pump는 최대10페이지·500행이며 페이지 사이200ms, 화면100개, 신호는 boolean 하나로 제한한다. 상한 도달 시 cursor는 마지막 확인 페이지에 남고 자동 진행을 멈추며 ‘계속 복구’로 재개한다. 고정 until 안의 마지막 페이지까지 읽기 전에는 복구 완료로 표시하지 않는다. 모든 검증/역순 페이지/범위 밖 행/중복 seq 불일치는 오류이며 cursor를 적용하지 않는다. 인증·방 전환 generation은 이전 응답/ack/finally/timer를 무시한다. cursor와 행은 계정/방별 메모리에만 보관하고 다른 계정/명시 logout은 삭제한다. 새로고침·기록 삭제·DB 복원은 별도 경계다.

## 재연결과 발송 상태

Socket.IO 자체 reconnection/retries는 끄고 hook이 lifecycle과 타이머를 소유한다. 연결 실패/끊김은500/1000/2000ms의 최대3회 재연결 뒤 멈춘다.401은 auth.expire,403/400/409/429는 자동 재시도 없이 원인을 안내한다.503과 transport 실패만 제한 재시도하며 수동 복구로 새 연결 예산을 시작할 수 있다.

각 계정의 방마다 미확인 발송1개만 메모리에 둔다. 허용 방이2개이므로 총2개 상한이다. 최초 제출 시 crypto.randomUUID를 만들고 text/room/user와 묶는다. ack timeout3초·503 뒤 같은 ID로 최대3회 추가 시도(500/1000/2000ms), 연결이 없으면 미확인 상태로 보존하고 다시 연결한 뒤 사용자가 재시도한다. 성공 ack만 ‘저장 확인’이며 이력 수신과 ID로 중복 표시하지 않는다. 상한 뒤 ‘결과 미확인’과 동일 ID 수동 재시도, 명시 취소를 제공한다. 같은 방의 서로 다른 내용 새 전송은 미확인 건을 해결/취소한 후 가능하다. 취소는 이미 저장한 행을 삭제하지 않는다. 같은 계정 재인증은 보존, 다른 계정/명시 logout은 폐기한다. 토큰/비밀번호·outbox를 localStorage에 넣지 않는다.

## 교재와 검증

A 저장 트랜잭션·idempotency, B Gateway 이력·현재 권한, C hook 복구·재시도/수명을3주로 나눈다. 시작 코드는 A repository fail-closed, B history 거부, C 연결/복구 미구현이며 인증·기존UI는 제공한다. 예측·실패 실험·공식 근거·설명3개·빈 제출·브라우저 미실행 양식을 제공한다. 독립 변경은 ‘서버 응답 유실을 겪은 미확인 발송을 이력의 clientMessageId로 확인 처리하되 다른 계정/방을 섞지 않기’이며 답을 제공하지 않는다.

실제 DB에서 동시 같은ID·내용충돌·다른사용자/방 범위·rollback·commit 순서·50개 경계·삭제 구멍·최소 권한을 검사한다. 실제 HTTP cookie/socket으로 저장 뒤 ack 유실·재접속·재전송1행·이력 권한·프로세스 재시작을 재현한다. UI는 transport fake로 timer 상한·이력/live 중첩·늦은낮은seq·복구 중 신호·cleanup·계정/방 소유를 검사한다. source-only 설치/빌드·기존0~5회귀·starter의도된 실패·Linux CI와 artifact 무결성도 확인한다. 측정값·브라우저 결과를 만들지 않는다.
