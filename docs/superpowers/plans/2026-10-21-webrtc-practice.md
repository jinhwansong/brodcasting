# 실제 WebRTC 송출·시청 실습 추가

사용자가 샘플 영상임을 확인한 뒤 ‘WebRTC 송출·시청 실습 추가’를 명시적으로 선택했다. 기존 계획의 WebRTC 제외는 이 추가 실습에 대해 해제한다. 알림5~7주·F1~F3·최종 검증도 계속 남아 있다. 현재 다크 UI는 유지하고 실제 송출 화면을 별도로 연결한다.

## 구현 경계와 순서

1. 기존 세션·같은 Origin 검사를 사용하는 별도 Socket.IO path /rtc.io, namespace /rtc를 만든다. 기존 채팅의8KB 제한을 유지하고 SDP용 별도 엔진만32KB로 제한한다. SDP는 실행/로그 저장 없이 검증 후 허용한 쌍에만 전달한다.
2. 로그인한 송출자가 자기 방을 연다. 방 ID는 서버 UUID다. 로그인한 시청자만 입장한다. 한 계정1송출·방4시청자·전체5방·연결20개로 제한한다. 송출자↔그 방의 시청자 사이에서만 offer/answer를 전달한다. 세션 만료/로그아웃·퇴장·끊김 때 관련 연결을 정리한다.
3. 별도 ICE 메시지 대신 ICE 수집 완료 후 SDP를 보내는 작은 방식으로 시작한다.8초 제한과 취소를 둔다. 외부 STUN/TURN을 자동 호출하지 않는다. 같은 기기/접근 가능한 LAN 직접 연결 실습이며 모든 인터넷 환경의 연결을 보장하지 않는다.
4. 테스트 화면은 canvas.captureStream으로 직접 생성한다. 실제 카메라/화면 공유도 사용자가 버튼으로 직접 선택하며, 자동 캡처/권한 수락을 하지 않는다. 종료/계정 변경/페이지 이동 시 트랙·타이머·peer·소켓을 해제한다. 미리보기와 수신 영상은 srcObject를 사용한다.
5. UI에 실제 방 목록·송출/중지·방 시청·연결 상태·실제 getStats 프레임을 제공한다. 샘플 파일 재생 화면과 구분한다. 시청자 수는 등록된 실제 접속 수이며 상한을 표시한다.
6. 먼저 입력·방 소유권·중계 쌍·상한·정리 검사를 실패시키고 구현한다. 실제 DB/세션/소켓 검사를 추가한다. 실제 두 브라우저 탭에서 테스트 화면의 WebRTC 송수신·프레임 증가·중지/정리를 관찰한다. 합성 테스트를 카메라·두 물리 PC 검증으로 바꾸지 않는다.
7. 기본은 loopback이다. 다른 PC용은 명시적인 LAN HTTPS 설정과 사용자가 신뢰한 인증서를 요구한다. 에이전트가 방화벽·공개 노출·인증서 경고를 우회하지 않는다. 준비 가능한 코드·설명은 완성하고 실제 다른 PC/신뢰가 필요한 단계는 정확히 구분한다.

이 방식은 송출자가 시청자마다 보내므로 업로드가 시청자 수에 따라 늘어난다. SOOP/치지직 규모의 SFU/CDN/P2P 중계 절약 구조가 아니며 직접 송수신을 배우는 소규모 실습이다. 새 미디어 서버/유료 자원/공개 배포/외부 부하는 추가하지 않는다.

공식 근거: https://webrtc.org/getting-started/peer-connections , https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/addTrack , https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/captureStream .

자체 검토: 기존 회원·채팅 권한을 넓히지 않고 송출자가 명시적으로 연 새 방에만 접속한다. 서버의 중계 검증이 클라이언트 target 값을 그대로 신뢰하지 않는다. 개인 화면/카메라 자동 수집과 SDP/IP 기록을 제외한다. 사용자 순차 실행 규칙으로 독립 서브에이전트 리뷰는 수행하지 않는다.
