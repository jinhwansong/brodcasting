# 알림5주 — 사용자별 영속 알림함

전체 승인 범위 R5를 순차 실행한다. 기존 세션·CSRF·직접 SQL과 BullMQ를 재사용하고 새 인증 방식은 만들지 않는다. 시작/완성/공개 검사/쉬운 교재/실제 증거를 함께 제작하며 학습0·미시작을 유지한다.

## 고정 동작

- 로그인한 본인만 알림 생성·목록·읽음·미처리 재접수를 요청한다. 수신 userId를 입력으로 받지 않는다. 생성은 정확히 clientKey(UUID v4)·body(공백 제외1~500자), 사용자별 같은 key는 같은 내용일 때 동일 사건 ID다. 다른 내용 재사용은409다.
- DB에 영속 사건(outbox)을 먼저 커밋하고 큐에는 사건 ID만 보낸다. 큐 장애여도 사건이 남으면202와 queued:false를 응답한다. 알림 도착 완료로 가장하지 않는다. 같은 사용자 사건100개를 상한으로 두고 새 접수는429로 제한한다.
- Worker는 사건을 DB에서 읽어 실제 알림함에 저장한다. 사건 행 잠금→기존 inbox 확인→사용자별 카운터 행 잠금/증가→알림 INSERT를 같은 트랜잭션으로 묶는다. 중복 작업은 같은 알림1개다. 사용자별 순번 할당과 커밋을 직렬화해서 더 작은 순번이 뒤늦게 커밋되어 복구 커서에서 누락되는 문제를 막는다.
- 목록은 본인 것만 고정20개, 기본/ before는 내림차순 과거 목록, after는 오름차순 새 알림 복구다. before·after는 동시에 받지 않고 bigint 범위의 정수 문자열로 검증한다. 목록 다음 경계는 순번이며 시각으로 경계를 만들지 않는다.
- 읽음은 본인 행만 UPDATE하고 최초 읽은 시각을 유지한다. 다른 사용자와 없는 ID는 모두404다. body/query에 예상 외 필드를 거부한다.
- Worker 시작 및 본인의 명시적 재접수에서 outbox 중 아직 inbox가 없는 사건을 다시 큐에 넣는다. queued_at만 믿으면 Redis 손실을 복구할 수 없으므로 inbox 존재를 기준으로 한다. 실패한 retained job은 명시적 재접수 때 retry한다. 재시도3회와 명시적 복구를 구분하고 무한 자동 재접수 루프는 만들지 않는다.
- 한 요청의 미처리 재접수는 최대50개, 한 사용자 사건100개, 큐 동시 처리1개, 완료/실패 기록100개 및 완료1시간 보관으로 실습을 작게 제한한다. 외부 메일·푸시·공개 서버는 호출하지 않는다.

## 구현과 검사 순서

1. runtime-05 독립 package와 최소 auth 선수 코드·스키마·가짜 발송 대신 inbox Worker·HTTP 준비 코드를 만든다. 과제는 deliver/list 두 함수로 고정한다.
2. 실제 DB/Redis 기반 검사를 먼저 실패시킨다. 생성 소유권·중복 키 충돌·유저 분리·경계 페이지·동시 중복 처리·롤백·읽음·큐 전달 공백/재시작 복구·로그아웃을 확인한다.
3. 같은 검사를 통과시키고 시작 코드에 의도된 실패가 남는지 분리한다. 안정 순번과 저장/큐의 실패 구간을 쉬운 말로 설명한다.
4. 작은 React 알림함에서 로그인·실습 알림 접수·새 목록·읽음·과거/새 항목 복구를 제공하고 실제 브라우저로 확인한다. 최종 온에어 사이트의 알림 통합은 R7/F 뒤에 이어간다.
5. 밖으로 복사한 소스만 새 설치·실제 검사·빌드하고 기존 스크립트/의존성·미추적 사용자 문서를 보존한다. 검증/원시 로그/제한을 기록한 뒤 커밋·브랜치 CI·main 순으로 게시한다.

자체 검토: 동일 DB 트랜잭션이 inbox의 중복·순번을 보장하는 범위만 주장한다. DB와 Redis를 하나의 트랜잭션으로 표현하지 않는다. 사용자 입력의 수신자·임의 큐 payload를 신뢰하지 않는다. Docker와 DB는 고유 소유 표식과 finally 정리를 사용한다. 다른 사람에게 실제 알림을 보내거나 계정 권한을 확장하지 않는다.
